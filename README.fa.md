قرارداد نقش‌ها، محدودهٔ دسترسی ابزارها و شروط تحویل مرحلهٔ سوم: [AGENT-CONTRACTS.md](docs/AGENT-CONTRACTS.md).

قرارداد دقیق API، پیام‌ها و ابزارها و روش اعتبارسنجی مرحلهٔ چهارم: [PROTOCOL-CONTRACTS.md](docs/PROTOCOL-CONTRACTS.md).

طراحی تفصیلی گراف، حافظه، بازیابی و نگهداری مرحلهٔ پنجم: [STATE-PERSISTENCE.md](docs/STATE-PERSISTENCE.md).

سقف‌های عددی اجرا، بودجه، اصلاح و لغو مرحلهٔ ششم: [EXECUTION-LIMITS.md](docs/EXECUTION-LIMITS.md).

## وضعیت فعلی

**در مرحلهٔ طراحی و پیش از MVP هستیم.** این مخزن فعلاً شامل تعریف پروژه و راهنمای مشارکت است؛ برنامهٔ اجرایی، Agent فعال یا اتوماسیون GitHub هنوز پیاده‌سازی نشده است.

## تجربهٔ موردنظر

کاربر درخواست خود را فقط با لید مطرح می‌کند. لید نیازمندی، معماری و معیار پذیرش را با او روشن می‌کند و سپس کار را به نقش‌های تخصصی می‌سپارد. فعالیت نقش‌ها، تصمیم‌ها، خروجی‌ها، تست‌ها و دفعات اصلاح در گراف و تاریخچه قابل مشاهده خواهند بود.

## ترکیب پیشنهادی MVP

| نقش | مسئولیت |
| --- | --- |
| Tech Lead / Architect | گفت‌وگو با کاربر، نیازمندی، معماری، تقسیم وظایف و بررسی نهایی |
| Frontend Developer | رابط کاربری، تعاملات، اتصال به API، تست و مستندات frontend |
| Backend Developer | منطق کسب‌وکار، API، پایگاه داده، کنترل دسترسی، تست و مستندات backend |
| QA / API Tester | تست مستقل رفتار و API، گزارش خطا و بررسی اصلاحات |
| Security Reviewer | بررسی امنیت طراحی و تغییرات، ثبت یافته‌ها و بررسی اصلاحات |

Frontend و Backend از MVP نقش‌های مستقل‌اند؛ فقط نقش لازم برای هر وظیفه فعال می‌شود. اجرا در ابتدا ترتیبی و ارتباط بر اساس قرارداد API و پیام ثبت‌شده است.
در نسخه‌های بعد، database، معماری، مستندات و CI/CD می‌توانند نقش‌های مستقل داشته باشند.

## روند پیشنهادی تحویل

۱. توافق کاربر و لید روی طرح و معیار پذیرش.

۲. تعیین وظایف، مسئول، وابستگی و خروجی هر کار.

۳. توسعه روی branch و ایجاد Pull Request همراه با تست و مستندات.

۴. اجرای بررسی‌های خودکار CI و سپس بررسی مستقل QA و امنیت.

۵. بازگرداندن خطاها به مسئول، اصلاح و اجرای مجدد بررسی‌های مرتبط.

۶. بررسی نهایی لید روی همان نسخهٔ کد و ارائهٔ نتیجه به کاربر.

۷. تصمیم کاربر دربارهٔ merge و انتشار.

## حافظه و قابلیت پیگیری

- وضعیت فعلی و مرحلهٔ بعدی اجرای کار.
- مسئول هر وظیفه و تحویل‌دهنده و تحویل‌گیرندهٔ آن.
- تصمیم‌ها همراه با دلیل و منبع.
- خروجی‌ها و گزارش تست متصل به نسخهٔ مشخص کد.
- ادامهٔ اجرا پس از توقف، با ثبت شکست‌ها و جلوگیری از تکرار بی‌دلیل عملیات.

این موارد هدف طراحی هستند و هنوز قابلیت اجرایی مخزن محسوب نمی‌شوند. انتخاب نهایی فناوری‌ها و محدودهٔ نسخهٔ اول در حال بررسی است.

## مشارکت

پیشنهادها را در Issues مطرح کنید و تغییرات را با branch جدا و Pull Request ارائه دهید. راهنمای کامل در [CONTRIBUTING.md](CONTRIBUTING.md) آمده است. اطلاعات حساس، کلیدهای API و حافظهٔ خصوصی پروژه‌ها نباید در مخزن منتشر شوند.
